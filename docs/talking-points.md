1. Why FastAPI for this API

I chose FastAPI because it collapses three jobs into one declaration. When I define a Pydantic model or type a query parameter, I simultaneously get validation at the border — bad input dies with a precise 422 naming the field before my code runs — automatic type conversion, and the interactive OpenAPI docs, all from the same source of truth, so they can never drift apart. The practical payoff showed up on day one: my entire interior — the scoring service especially — never defensively re-checks anything, because invalid states like a negative price or an affinity above 1 physically can't get past construction. The second reason was dependency injection: every router receives its service through Depends(), which gave me a single seam where the in-memory store swaps for DynamoDB without touching a router or a test. The honest caveat: if this app needed an admin panel and a relational ORM out of the box, Django's batteries would've argued back — FastAPI won because this is a lean, typed, JSON-speaking service where the contract is the product.

2. Why every score carries evidence

Every factor in my scoring engine returns two things: a number and a sentence — "8 favorites on the lineup, 2 already covered," "$220 ticket plus ~$60 drive, $280 all-in." That's a deliberate API contract, not decoration, and I enforce it with a test: the six factor contributions must sum to the total score, and every factor must carry a non-empty evidence string — it runs as its own named stage in CI. The reasoning is about trust in decision-support tools: an opaque score gets ignored the first time it contradicts a user's intuition, but a score that shows its math gets argued with, tuned, and ultimately used. It also kept me honest as the builder — when a ranking looked wrong during development, the evidence strings let me see in seconds whether the data, the weights, or the formula was to blame.

3. The lineup-scoring redesign (the "decision you changed" story)

My first design borrowed a sales-world assumption: marginal value — once an artist was covered in your circuit, seeing them again was worth 65% less, then 85% less. Then I tested the scorer against my own actual taste and the assumption broke: for music fans, repeat viewings hold most of their value — seeing a favorite a third time is a feature, not redundancy. So I redesigned it count-first: every favorite on a lineup earns a large presence value plus a smaller affinity topping, which mathematically guarantees that a festival with five mid-tier favorites outranks one with just my top two. The old idea didn't die — it became a knob: a novelty-decay setting, defaulting to a gentle 10% compounding discount per prior viewing, tunable to zero or to strong-variety. Shipping it surfaced one more bug worth mentioning: a hard cap at "five favorites = max" was swallowing the dilution on stacked lineups, so I replaced it with a tanh soft-saturation curve — more favorites always helps, just less and less. The sequence I'd defend in a design review: strong assumption, tested against a real user — me — softened into a preference, with the behavior pinned by a test that checks both knob positions.

"Walk me through your DynamoDB design."

I designed the table backward from the questions, not forward from the entities — that's the core discipline with DynamoDB, because it only answers instantly-findable questions, so the access patterns are the schema. I wrote down eleven of them before touching code: get an event with its lineup, its updates newest-first, browse by region and month, my ranked recommendations, my circuit with add and remove, all events for a given artist in date order, plus favorites, friends, RSVPs per event, artist metadata, and — the one people forget is an access pattern — the recompute that rewrites recommendations whenever the circuit or an RSVP changes.

It's a single table with two item families. Everything about an event files under one partition key — EVENT#id — with the sort key acting as shelves: META for the core record, ARTIST#id per lineup slot, UPD#timestamp for the updates stream, RSVP#friend for crew signals. So "get the event" is one Query returning the whole item collection, and the updates stream is a sort-key range slice — ISO timestamps sort correctly as text, so chronological order comes free. Everything about me files under USER#me on its own shelves: legs with the date in the sort key so the itinerary reads out pre-sorted, favorites, friends, and recommendations. RSVPs deliberately live under the event's key, not mine, because the only reader is the scoring factor asking "who's coming to this event" — in this model, where a fact lives is decided by who reads it, not by what owns it.

Two design moves I'd call out. First, recommendations are materialized with an inverted score in the sort key — I store 100 minus score, zero-padded, so ascending sort-key order is best-first. The board read is one Query, already ranked; correctness doesn't depend on any reader remembering a sort flag. The trade is a recompute on every circuit or RSVP write and a brief staleness window during the rewrite — the right trade here, because the board is read constantly and written rarely. Second, the many-to-many between artists and events is an inverted index: the lineup-slot item that answers "who plays this event" on the base table carries GSI attributes so the same item answers "where does this artist play, in date order" on GSI2. One item, two directions, no duplication. A second GSI keys event metadata by region and date for the browse pattern.

I have receipts for both the design and its cost model. The storage swap ran under the same eight API tests, unchanged — the store sits behind a service interface, so routers and tests never knew. And I benchmarked the index against the alternative at 5,000 events: the GSI Query examined roughly thirty items to find an artist's gigs; a Scan with a filter examined all fifty thousand to return the same answer — and on real AWS you're billed for items examined, not matched, so that's not just latency, it's a few-thousand-fold cost difference.

Known edges, because every design has them: my all_events walk does an N+1 — one Query per event when the scorer runs — fine at this scale, flagged in review with two escape hatches (denormalize lineup onto META, or batch-get). The recompute's delete-then-write isn't atomic; a transaction closes it if it ever matters. And if this app needed ad-hoc analytical queries — "average ticket price by genre by month" — I'd stop torturing DynamoDB and put a warehouse beside it. Knowing where the tool stops is part of the design.

"Why one table instead of eight?" (item collections: things fetched together arrive in one request; cross-"table" consistency of a single write; and the honest flip — single-table costs you query flexibility, which is fine because I enumerated the questions first). "What happens when a second user shows up?" (USER#me becomes USER#<id> — the design is already partitioned per user; the real new problem is recompute fan-out when a shared event changes, which wants a queue). "Your GSI uses Projection: ALL — why, and what's the trade?" (reads never double-fetch; the cost is storing full copies in the index — INCLUDE with just the id would halve GSI storage but force a follow-up fetch per hit; at my read patterns, ALL wins, and I'd revisit if the items grew fat). "When would the inverted-score trick bite you?" (score ties collide unless the event id in the SK breaks them — it does; and if scores could exceed the padding range the text-sort breaks — mine's clamped 0–100 with fixed width).
